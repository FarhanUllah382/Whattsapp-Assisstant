02 / End-to-end message workflow

Two routes. One controlled delivery path.

The normalized sender number selects the customer or owner path. Each message is processed inline; there is no durable inbound queue.

OPEN · Load context

Customer turns save the inbound text and load 20 recent messages, the rolling summary, and durable-note headlines.

LOOP · Act through tools

Up to six model/tool steps. Plain model output is not delivered; the send tool must succeed.

CLOSE · Preserve context

Customer turns save a summary and new notes, then validate missed bookkeeping or record a handoff.

Owner turns expose four read-only business reports plus a send tool. They save transcripts but do not load customer memory or create checkpoints. HTTP 200 means handling completed; delivery can still have been blocked.

03 / Retail domain

Conversations become business records.

Orders move through a forward-only lifecycle. Inventory reservation, payments, and account balances remain explicit business operations.

Financial effects

EventPersisted effect
Place orderCreate order + debit; stock unchanged.
ConfirmReserve stock by subtracting quantities.
Record paymentPost customer credit. Order status is a separate action.
CancelReverse the debit; restore stock if reserved. Payments remain credited.

Owner intelligence

QuestionSource of truth
Today's salesToday's non-cancelled order value, not cash receipts.
Who owes?Positive customer ledger balances, highest first.
Best sellerMost units in non-cancelled orders, all time.
Follow-upsPlaced/confirmed orders aged ≥2 days; overdue at ≥7 days.
Balance = debits − credits. Positive means money owed; negative means store credit. This is a customer debit/credit ledger. It does not implement a complete double-entry general ledger or bank settlement verification.

04 / Data architecture

One database. Clear responsibilities.

Ten tables separate identity, retail records, conversation memory, and processing receipts. Reports are calculated from current data.

Business facts

Orders store item snapshots in JSON. Product references inside that JSON are application-validated, not SQL foreign keys.

Conversation memory

Transcripts retain messages. One checkpoint is replaced at close; durable notes store longer-lived customer facts.

Retry receipts

With a provider event ID, one transaction commits an order/payment effect and its saved result. A retry reuses that result.

Receipt protection is scoped to one order and one payment result per provider event. Missing message IDs bypass it. It does not deduplicate the whole conversation, notes, handoffs, or every outbound variation.

05 / Deployment & operational boundaries

Local runtime. External intelligence.

The recorded development setup runs the application on the host and the WhatsApp gateway inside Docker Desktop.

Implemented controls

Customer sends use pacing, repetition checks, discount rules, and handoff checks. Owner sends share pacing and the in-process send lock. Default send window: 07:00–22:00 Asia/Karachi.

Reliability boundary

Node v24 / better-sqlite3 native crash: mitigated, not fixed. The development loop restarts the worker. Order status, stock, and reversal writes remain separate statements.

ScopeCurrent boundary
Human handoffDatabase row + structured log. Automated owner WhatsApp alerts remain unbuilt.
Delivery & trustNo durable scheduling queue; external send and local success write are not atomic. The webhook relies on trusted gateway input and has no signature middleware.
